# public/art/ — real, loaded game art assets

This directory holds real PNG (and, from Phase 74 onward, PNG+JSON atlas)
assets loaded through Phaser's normal texture pipeline, per the approved
visual overhaul plan at `docs/phase_73_to_78_visual_overhaul_plan.md`.

Everything here is served by Vite directly from `public/` (no build-time
processing), at `/art/<file>` in dev and copied verbatim into `dist/art/` on
`npm run build`.

Phase 76 raised `WILDLIFE_SPRITE_SIZE` (`src/config/wildlifeConfig.ts`) from
12px to **18px**, matching Phase 75's `ANIMAL_SPRITE_SIZE`/`RAIDER_SPRITE_SIZE`
bump (this constant was deliberately left at 12px in Phase 75, deferred to
Phase 76 since it's an independent literal, not an alias). Like
`ANIMAL_SPRITE_SIZE`, this is a texture-generation/loading size only -
wildlife sprites are placed centred and never `setDisplaySize`d. Real
AI-generated art for `wildlife-atlas.png` must be authored at 18x18, not the
old 12x12. `RAIDER_CAMP_SPRITE_SIZE` (24px) is unaffected by this change - it
is an independent literal, not part of the 12px small-unit size class.

**§5f note (raider-Coyote vs. wildlife-Coyote differentiation):** the plan's
§5f resolved that these two must be visually distinguishable even as
placeholders, so a future real-art pass has the pattern already established.
Both share the same base tan/brown color (`[0xbf, 0xa9, 0x80]`) so they still
read as "the same animal", but `raider-Coyotes` alone gets an extra horizontal
red bandana-stripe band near the top third of the frame - a placeholder stand-
in for the plan's real-art direction of giving the raid-faction Coyote a
bandana/scar marker. When real art replaces this atlas, replicate the same
concept (a bandana, scar, or similar hostile-marking accent on the raid
version only) rather than two identical Coyote sprites.

Phase 75 also raised the small-unit texture-generation size from 12px to
**18px** (`ANIMAL_SPRITE_SIZE` in `src/config/buildingConfig.ts`, and its
aliases `VILLAGER_SPRITE_SIZE`/`COWBOY_SPRITE_SIZE`/`BRAWLER_SPRITE_SIZE`/
`DYNAMITER_SPRITE_SIZE`/`RAIDER_SPRITE_SIZE`; `MOUNTED_COWBOY_SPRITE_WIDTH`/
`HEIGHT` scaled proportionally 16x12 → 24x18). This is a real, permanent
rendering-size change independent of the placeholder-vs-real-art distinction
above — real AI-generated art for these 6 atlases must be authored at 18x18
(24x18 for the mounted-cowboy frame), not the old 12x12/16x12.

**Accents note (Phase 77, plan §5b.2 accent carve-out alignment risk):** the
6 accent frames above are pieces conceptually "carved out of" their parent
building sprite, positioned at hardcoded pixel offsets in `MainScene.ts`
(e.g. `WellCrank` at `originX+16, originY+2`; `Campfire` at `originX+4,
originY+46`, outside the Barracks' 64x64 footprint, in its yard). Because
`buildings-atlas.png` is itself still Phase 74 PLACEHOLDER flat-color art (not
final art), there is no real "hole" in the current building sprites for these
placeholder accents to visually plug — Phase 77's job was only to get each
accent's frame SIZE and NAME correct (so `MainScene.ts`'s existing
`createAccentImage`/per-accent wrapper methods and their `setOrigin`/tween
calls, all byte-identical to before this phase, resolve to a correctly-sized
image) and to prove the non-square shapes (`16x4`, `64x8`) round-trip through
the atlas packer correctly. A **future** phase — after both real building art
AND real accent art exist — must verify actual pixel alignment (does the real
`WellCrank` art actually sit over a real crank-shaped cutout in the real Well
sprite?); that verification was NOT possible in Phase 77 and was not
attempted. When authoring real accent art, author the building + its accent as
one image first, then split it (per the plan's §5b.2 mitigation), rather than
generating them independently.

## Why a placeholder

Phase 73 built the complete loading pipeline (folder structure, `BootScene`
load path, `gameConfig`'s `pixelArt: true`, the loading progress bar, and the
`tools/verify-asset-dimensions.mjs` dimension-check tool) but no
AI-image-generation tool was available in the environment that implemented
it. `tiles-atlas.png` is a functional stand-in only — correct file path,
correct dimensions, correct frame order/count — so the tilemap renders and
the pipeline can be proven end-to-end. It is **not** an attempt to replicate
the target art style described in the plan's §2 (hand-painted pixel art,
locked Western palette, top-left lighting, etc.).
